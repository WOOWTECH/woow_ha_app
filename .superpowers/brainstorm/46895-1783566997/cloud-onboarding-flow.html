插入策略選擇

CloudChooser 要怎麼插入現有的 navigation graph？

A

方案 A：替換 startDestination

在 OnboardingNavigation.kt 的 onboarding() 函式裡，把 startDestination 從 WelcomeRoute 改成 CloudChooserRoute（當 !skipWelcome 時）。CloudChooser 選「本地」後 navigate 到 WelcomeRoute，選「雲端」navigate 到 CloudSignInRoute。

優點

  • 改動最少，只動一行 startDestination + 新增 3 個畫面
  • 完全不動 Welcome/ServerDiscovery 既有邏輯

缺點

  • CloudChooser 變成同一個 nav graph 裡的 startDestination，語義上稍微不直覺（它不是真正的 "onboarding" 第一步，而是一個前置選擇）
B

方案 B：在 LaunchViewModel 層做分流

不動 OnboardingNavigation.kt 的 startDestination。改在 LaunchViewModel.navigateToOnboarding() 之前，先 emit 一個新的 CloudChooserRoute。選「本地」後才呼叫原本的 navigateToOnboarding()。

優點

  • onboarding 的 nav graph 完全不變
  • CloudChooser 在概念上是 onboarding 之前的獨立步驟

缺點

  • 需要改 LaunchViewModel 和 HANavHost，動到更高層的檔案
  • 任務規格說「不要動既有的本地流程」，改 LaunchViewModel 有觸碰範圍邊界的風險
C

方案 C：嵌套 navigation graph

建一個新的 cloudOnboarding nested nav graph，包含 CloudChooser → CloudSignIn → CloudProvision 三個畫面。在 onboarding() 裡把它註冊為一個子圖，startDestination 指向這個子圖。

優點

  • 三個新畫面的 navigation 完全封裝在自己的子圖裡
  • 未來擴充（加步驟）很乾淨

缺點

  • 增加架構複雜度，目前只有 3 個畫面可能 over-engineering
  • 跨子圖 navigate 到 WelcomeRoute 需要額外處理

我推薦方案 A — 改動最小、風險最低、完全遵守「不動既有流程」的原則。點選你偏好的方案。
